## 1. 产品定位回顾

晓诗是一款**古诗词学习 App**，核心用户是：

| 用户类型 | 场景 | 需求 |
|----------|------|------|
| 学生 | 按教材查找诗词 | 需要朝代、体裁、作者等结构化分类 |
| 爱好者 | 浏览品鉴 | 需要主题、意象、情感等柔性标签 |
| 运营人员 | 内容管理 | 需要高效的内容组织和批量操作能力 |

**分类和标签是内容组织的两条轴线**：
- **分类** = 骨架（刚性、层级、唯一）
- **标签** = 血脉（柔性、网状、多元）

## 2. 内容组织模型

### 2.1 诗词的多维属性

一首诗词可以从多个维度描述：

```
                     ┌─ 朝代（唐/宋/元/明/清）
                     ├─ 体裁（五言绝句/七言律诗/词/曲）
        刚性维度 ────┼─ 作者
                     ├─ 出处（诗经/唐诗三百首/宋词三百首）
                     └─ 年级（小学/初中/高中）
                    
                     ├─ 主题（思乡/送别/边塞/咏物）
                     ├─ 情感（豪放/婉约/悲壮/闲适）
        柔性维度 ────┼─ 意象（月亮/杨柳/梅花/流水）
                     ├─ 节日（春节/中秋/重阳/清明）
                     └─ 场景（登高/送别/宴饮/独处）
```

**设计决策**：哪些走分类，哪些走标签？

| 判断标准 | 走分类 | 走标签 |
|----------|--------|--------|
| 一首诗的该属性数量 | 只能 1 个 | 可以多个 |
| 是否需要层级 | 是 | 否 |
| 变更频率 | 低（预设体系） | 高（随时新增） |
| 是否影响导航结构 | 是（出现在主导航/筛选器） | 否（辅助筛选） |

### 2.3 晓诗的标签体系

标签不设预设分类，运营可自由添加。但建议按以下**隐含维度**组织：

| 维度 | 示例标签 | 用途 |
|------|----------|------|
| **主题** | 思乡、送别、边塞、咏物、怀古、爱情、闺怨 | 内容分类 |
| **情感** | 豪放、婉约、悲壮、闲适、孤独、豁达 | 风格筛选 |
| **意象** | 月亮、杨柳、梅花、流水、青山、鸿雁 | 意象检索 |
| **节日** | 春节、元宵、清明、端午、中秋、重阳 | 节日运营 |
| **场景** | 登高、送别、宴饮、独处、征战、归隐 | 场景推荐 |
| **教材** | 小学必背、初中必背、高中必背 | 学习路径 |
| **作者** | 李白、杜甫、苏轼、李清照 | 作者聚合 |

> **设计决策**：作者是否应该作为标签？
> 
> **建议**：作者**不走标签**，因为有独立的 authors 表和作者管理功能。标签应聚焦在「主题/情感/意象」等**内容属性**上。

### 3.2 运营人员：分类管理

**核心场景**：
1. 新增一个朝代/体裁分类
2. 调整分类层级（如将「乐府」从「唐诗」移到独立顶级）
3. 查看每个分类下的诗歌数量，评估内容覆盖

**操作原则**：
- 分类变更影响面大，需要二次确认
- 删除前必须检查关联数据
- 排序值控制前端展示顺序

### 3.3 运营人员：标签管理

**核心场景**：
1. 为新录入的一批边塞诗批量添加「边塞」标签
2. 发现「送别」和「离别」是同义词，合并标签
3. 清理无诗歌关联的冗余标签
4. 查看热门标签，了解内容分布

**操作原则**：
- 标签创建门槛低，输入即可
- 支持合并操作（将 A 标签合并到 B，删除 A）
- 支持查看标签下的诗歌列表

### 3.4 C 端用户视角（运营可感知）

虽然本后台不直接服务 C 端，但运营的操作会影响 C 端体验：

| 后台操作 | C 端影响 |
|----------|----------|
| 设置诗歌分类 | C 端可按分类浏览（「唐诗 > 五言绝句」） |
| 设置诗歌标签 | C 端可按标签筛选、看相关推荐 |
| 删除标签 | C 端该标签页面消失，关联诗歌不显示此标签 |
| 删除分类 | **不允许**（有诗歌时禁止删除） |

## 6. 边界场景与处理策略

### 6.1 分类相关

| 场景 | 处理策略 |
|------|----------|
| 删除有诗歌的分类 | ❌ 禁止删除，提示「该分类下还有 N 首诗歌」 |
| 删除有子分类的分类 | ❌ 禁止删除，提示「请先删除子分类」 |
| 将 A 的父级设为 A 的子分类 | ❌ 禁止，检测循环引用 |
| 移动分类到新的父级 | ✅ 允许，子分类跟随 |
| 一首诗的分类被删除 | 后端约束：RESTRICT 或 SET NULL（建议 SET NULL） |

### 6.2 标签相关

| 场景 | 处理策略 |
|------|----------|
| 创建重名标签（不区分大小写） | ❌ 提示「标签已存在」 |
| 删除有诗歌关联的标签 | ⚠️ 允许，但提示「将从 N 首诗歌移除」 |
| 诗歌删除后标签残留 | 关联表 CASCADE 自动清理 |
| 标签名称含特殊字符 | 允许，但 trim 空格 |
| 标签合并 | 将 A 的所有关联迁移到 B，删除 A |

### 6.3 批量操作

| 场景 | 处理策略 |
|------|----------|
| 批量导入时分类不存在 | 使用默认分类，或创建失败记录 |
| 批量导入时标签不存在 | 自动创建标签（配置开关） |
| 批量添加已存在的标签 | 去重，不重复关联 |

- 无标签时显示「暂无标签」

## 10. 设计决策记录（ADR）

### ADR-001：朝代作为分类树的一部分，而非独立字段

**背景**：诗歌有朝代属性（唐/宋/元/明/清），可以设计为独立字段或融入分类树。

**决策**：将朝代融入分类树的顶层。

**理由**：
1. 朝代天然有排序（时间线），与分类的 sort 值吻合
2. 朝代下有体裁层级，树状结构自然表达
3. 减少字段数量，简化诗歌编辑页
4. C 端「按朝代浏览」等价于「按顶级分类浏览」

**后果**：
- 无法直接「跨朝代筛选所有五言绝句」（需要搜索功能补偿）
- 朝代变化时需要调整分类树（但朝代体系稳定，几乎不会变化）

---

### ADR-002：标签不设预设分类维度

**背景**：标签可以按维度分组（主题/情感/意象/节日...），也可以完全扁平。

**决策**：标签不设预设分类维度，保持扁平。

**理由**：
1. 降低运营门槛——不需要先理解维度体系
2. 避免维度选择的认知负担
3. 标签数量增长后，维度边界会模糊
4. 搜索功能可以替代维度分组

**后果**：
- 运营可能创建维度混乱的标签（如同时创建「思乡」和「月亮」）
- 需要后期通过标签治理来规范（Phase 3）

---

### ADR-003：作者不走标签

**背景**：作者可以作为标签（方便按作者筛选），也可以走独立 authors 表。

**决策**：作者走独立 authors 表，不走标签。

**理由**：
1. 作者有独立管理页面（含简介、朝代、头像）
2. 作者有查重、合并等复杂操作
3. 标签系统不支持作者的丰富元数据
4. 一首诗的作者只有一个，走标签浪费多选能力

---

### ADR-004：删除分类采用 RESTRICT 策略

**背景**：分类被删除时，关联诗歌如何处理？

**决策**：有诗歌时禁止删除分类（RESTRICT）。

**理由**：
1. 分类是诗歌的核心归属，不应出现「无分类」诗歌
2. 自动 SET NULL 会导致数据不一致
3. 强制运营先处理诗歌，保证数据完整性

**后果**：
- 运营需要先手动转移诗歌，再删除分类
- 这是有意为之的「摩擦点」，防止误操作
